## 速览

>- **菲涅尔本来描述的是"掠射角反射率上升"，边缘光只是借它的形状。** Schlick 近似 `F = F0 + (1−F0)(1−cosθ)^5` 取 `F0 = 0` 后退化成纯形状函数 —— 它不再是反射率、不满足能量守恒，只是一个轮廓蒙版。
>- **`N·V` 度量轮廓可见性。** 它是视线与法线夹角的余弦：球面上随离轮廓的距离连续变化，平面上是常数（整面同亮或同暗），薄几何上恒接近 0。
>- **`pow(fresnel, P)` 是分布整形，不是亮度。** 它把等值线在角度轴上平移：输出 ≥ 峰值一半的像素满足 `θ ≥ acos(1 − 0.5^(1/P))`，`P = 3` 时是 78.1°；`P → ∞` 上界趋近 90°，收益递减；`P = 0` 会让这个变量彻底消失。
>- **`dot` 的准确性建立在"两个单位向量"上。** `(kN)·V = k(N·V)` 说明长度误差是**乘性**的：边缘不是变亮一点，而是**位置整体偏移**。顶点插值会缩短向量，所以归一化必须逐像素做。
>- **发射项（emission）是光照方程的加法尾巴，加在 `lightingColor *= albedo` 之后**（URP `ShaderLibrary/Lighting.hlsl:181` → `:185`）。这一个位置单向推出：**不乘 albedo**（黑体也能发光）、**不吃阴影与 AO**、**不进实时光照传输**。

## 1. 菲涅尔效应与 Schlick 近似

**它是什么。** 菲涅尔效应描述电磁波在两种介质界面上的行为：**反射率随入射角变化**。垂直入射时反射率最低（空气到玻璃约 4%），入射角越接近 90°（掠射），反射率越接近 100%。这就是为什么侧看水面像镜子、正看水面能看到水底。它属于**着色/BRDF 层**的物理规律，与引擎无关，与光照强度也无关。

**取值与语义。** 精确的菲涅尔方程要分别处理 s 偏振与 p 偏振两个分量，工程上普遍改用 **Schlick 近似**：

```text
F(θ) = F0 + (1 − F0) · (1 − cos θ)^5
```

| 部件 | 语义 | 典型取值 |
|---|---|---|
| `F0` | 垂直入射（θ = 0）时的基础反射率，即"这个材质本身就反射多少" | 空气/水/玻璃等电介质约 0.02–0.05；金属 0.5–1.0（金、铜、铝各自不同，且是**有色**的） |
| `(1 − cos θ)` | 掠射程度：正对为 0，完全侧对为 1 | `[0,1]` |
| `^5` | 分布整形：把上升压缩到只剩最贴边的一段 | 固定 5 次 |

⚠️ 这里的 `θ` 严格来说是**视线与微面法线（半角向量）的夹角**，不是与几何法线的夹角。用几何法线代入是一个近似：它把"掠射程度"从微面统计量降级成纯几何量 —— 代价是不再严格，好处是不需要 BRDF 数据、不需要光源、不需要微面分布，一个 `dot` 就能算。

**底层机制。** 三个设计点值得单独说清：

1. **为什么可以只用 5 次幂。** Schlick 的做法是用 `(1 − cos θ)^5` 去拟合真实菲涅尔曲线：端点精确（θ = 0 时得 `F0`，θ = 90° 时得 1），中间偏大或偏小一点，但对渲染足够。它是**为实时着色设计的拟合**，不是推导结果。
2. **为什么边缘光会把 `F0` 丢掉。** `F0` 是**常数偏置**：它在整个表面（包括正对相机的中心）都加了一份基线亮度。对真实玻璃球那是正确的；但对一个刻意夸张的"边缘光"效果，它等于给整块表面铺了一层灰。取 `F0 = 0` 后公式退化为：

```text
F0 = 0  ⇒  F(θ) = (1 − cos θ)^5
```

只剩下"掠射程度"这一个变量，再用可调的 `_RimPower` 替换固定的 5 次幂，就得到边缘光要的形状函数。

```hlsl
half fresnel = 1 - saturate(dot(N, V));      // 掠射程度，与光源无关
half3 rim    = _RimColor.rgb * _RimColor.a * pow(fresnel, _RimPower) * _RimIntensity;
```

3. **`[HDR] Color` 与 `Color` 的区别**（顺带）：`[HDR]` 只影响 Inspector 的取色器与取值范围（允许 > 1），不影响通道数，也不做任何钳制。能否超过 1 完全由后面的颜色缓冲格式决定。

**可观察现象与边界。** 丢掉 `F0` 意味着丢掉了"垂直入射也反射一点"这个物理含义，因此：

- 它**不是能量守恒的 BRDF 项** —— 它不乘 `N·L`、不除以 π、不参与 kD/kS 的分配，也不与其它光照项竞争能量。你没法用"它会不会让物体变亮"来判断它是否正确，因为它根本不描述反射。
- 它**对光源一无所知**：不随主光方向变化，不被 shadow map 影响，也不会因为环境光变暗而减弱。
- 想要真实反射（金属/玻璃的观感），要走 GI / 反射探针那条路；边缘光只负责"轮廓的可见性提示"。
- 边界：掠射角在真实世界中还会带来偏振与全内反射，Schlick 近似不处理这些；`θ → 90°` 时值趋近 1，是渐近的，永远取不到 1 以外的值。

## 2. `N·V` 的几何含义：为什么它度量"轮廓可见性"

**它是什么。** `N` 是表面法线，`V` 是从该点指向相机的单位向量（URP 的约定方向，见 §4）。两者点积就是夹角余弦。这是一个**纯几何量**，属于光栅化/着色层，不涉及任何光照模型。

**取值与语义。** 单位向量时 `N·V = cos θ ∈ [−1, 1]`；`1 − N·V ∈ [0, 2]`；再套一层 `saturate` 就落在 `[0, 1]`。

| 视线与表面的关系 | `θ` | `cos θ` | `1 − N·V` | 含义 |
|---|---|---|---|---|
| **正面直视**：视线与法线同向，视线垂直于该点的切平面 | 0° | 1 | **0** | 完全看得见这一小片表面 |
| 斜视 | 0°–90° | 0–1 | 0–1 | 逐渐"侧过去" |
| **正切侧看**：视线落在切平面内，与法线垂直 | 90° | 0 | **1** | 这一小片表面正处在轮廓上 |
| 从背面看（`Cull Off` / 双面材质） | > 90° | < 0 | > 1 | 背面，靠 `saturate` 兜回 1 |

两种极限的物理图像值得记住：**视线与切平面垂直**时你在"正视"它，表面完全朝向相机；**视线落在切平面内**时你在"侧看"它，这一片表面在屏幕上被压成一条线 —— 它恰好处于**可见与不可见的交界**，也就是轮廓。所谓"轮廓可见性"，指的就是这个从"完全可见"到"即将不可见"的连续过渡。

**底层机制。** 关键点是：`1 − N·V` 与相机位置、形状、光照全都无关，**只由相机与法线决定**。

- 曲面上法线是连续变化的，于是 `N·V` 也连续变化，形成一张逐像素的标量场；相机一动，整张场跟着动（因为 `V` 是逐像素的）。
- 正因为它是标量场，后面所有操作（幂函数、阈值、加法）都是**对场的重映射**，而不是"给颜色加一笔"。这是边缘光与描边（几何外扩）在机制上的分水岭。
- 它天然是**视图相关**（view-dependent）的：换一个观察角度，亮区跟着轮廓一起移动。

**可观察现象与边界。**

- **曲面（球、胶囊、圆角）**：法线从指向相机连续转到垂直视线，亮区是一圈贴着轮廓内侧的环带，中间暗、边缘亮。
- **平面（立方体的一个面）**：面法线是常量，面上各像素的 `V` 只有轻微差异，于是 `N·V` 近似常量 —— **整个面要么整体偏亮、要么整体不亮**。这是定义的推论，不是权重算错了。
- **薄几何（机翼、帆、薄板）**：即使正对相机，其上表面相对视线也几乎是掠射的，`1 − N·V ≈ 1`，于是**整条亮**。同样是定义，不是过曝。
- **硬边**：逐像素法线在棱处不连续，边缘光会在棱上"断一下"。几何外扩型描边可以用位置平均法线修，标量场型边缘光**没有对应解法** —— 它用的就是那张不连续的几何法线。
- **法线退化或压平**（几何法线退化、法线贴图强度为 0）：场变成常数，效果退化成整块染色。此时该查数据，而不是调 `_RimPower`。
- ⚠️ 一条实践判据：**如果"边缘光"看起来是一整块亮斑而不是一圈，先怀疑梯度没了，而不是先怀疑参数。**

## 3. 幂函数对分布的整形：`pow(x, P)`

**它是什么。** `pow` 是定义在 `[0,1]` 上的单调重映射。它属于**数值整形**层：不改变端点的值，只改变中间区域的占比。在着色里它最常见的用途不是"调亮度"，而是"调分布的宽窄与陡峭程度"。

**取值与语义。** 端点不动：`pow(0, P) = 0`、`pow(1, P) = 1`。中间被这样重映射：

| 指数 | 效果 | 直观含义 |
|---|---|---|
| `P < 1` | 把中间值**抬高**（`0.0625^0.25 = 0.5`） | 亮区变宽，趋近整面染色 |
| `P = 1` | 恒等，什么都不改 | — |
| `P > 1` | 把中间值**压低**（`0.25^3 = 0.0156`） | 只有最接近 1 的一小段还有可观输出 |

把它作用到 §2 的标量场上，`P` 决定的就是**等值线在角度轴上的位置**。以"输出衰减到峰值一半"为判据：

```text
pow(fresnel, P) = 0.5
  ⇔  fresnel = 0.5^(1/P)
  ⇔  1 − cos θ = 0.5^(1/P)
  ⇔  θ = acos(1 − 0.5^(1/P))
```

| `_RimPower` | 需要的 `fresnel` | 夹角阈值 `θ` | 亮区范围 | 观感 |
|---|---|---|---|---|
| 0.25 | ≥ 0.0625 | **20.4°** | 20.4° – 90° | 几乎没有暗区，接近整块染色 |
| 1 | ≥ 0.5 | **60.0°** | 60.0° – 90° | 很宽的渐变 |
| **3（常用）** | ≥ 0.7937 | **78.1°** | 78.1° – 90° | 贴着轮廓的一圈 |
| 5 | ≥ 0.8706 | **82.6°** | 82.6° – 90° | 更细的线 |
| 8 | ≥ 0.9170 | **85.2°** | 85.2° – 90° | 极细，只剩最外一圈 |

⚠️ 判据里指数在**分母**上：`P = 0.25` 对应的是 `1 − 0.5^4 = 0.9375`，不是 `1 − 0.5^0.25`。写成 `1 − 0.5^P` 会把 `P = 0.25` 的阈值算成约 66°（实际 20.4°），整张表的趋势都会反过来。

**底层机制。**

1. **等值线平移，而非缩放。** 因为端点固定，`pow` 不会改变"最大/最小亮度"，只会让某条等值线前后移动。想改亮度是乘 `_RimIntensity` 的事，两者正交。
2. **收敛于 90°。** `P → ∞` 时 `0.5^(1/P) → 1`，于是 `θ → 90°`。90° 是渐近上界，永远到不了 —— 因为 `fresnel` 的取值上限就是 1。
3. **收益递减**（角度宽度 = `90° − θ`）：

| `P` | 3 | 5 | 8 | 10 |
|---|---|---|---|---|
| 亮区宽度 | 11.9° | 7.4° | 4.8° | 3.8° |
| 相比上一档收窄 | — | 4.5° | 2.6° | **1.0°** |

4. **`pow` 在 GPU 上的实现**：通常是 `exp2(y * log2(x))`。这带来两个后果：`x ≤ 0` 时**未定义**（实践常返回 NaN），以及非整数指数下的精度损失。所以底数必须先被钳到 `(0,1]`。
5. **为什么下限不能取 0**：`pow(x, 0) ≡ 1`（对 `x ∈ (0,1]` 恒成立），整个 `fresnel` 变量**消失**，输出退化成 `_RimColor.rgb * a * _RimIntensity` —— 一个与几何、相机、法线全都无关的常数。那不是边缘光，是给物体换了个颜色。下限取 0.25（阈值 20.4°）是"还能看出是渐变"的最后一档：**这不是精度保护，是语义保护**。

**可观察现象与边界。**

- `P` 太大（> 8）时亮线在屏幕上只有几个像素，法线精度、抗锯齿与 mipmap 的影响开始主导，线会闪烁或断裂。
- 要"更细的线仍然可见"，正确手段是提高 HDR 亮度并让 Bloom 溢出，而不是继续加 `P` —— 加 `P` 只会让线先变细再消失。
- `P < 1` 时整个表面被抬高，观感是"整体染色"，且因为数值接近 1，HDR 部分的动态范围被压缩。
- 边界：`pow` 无法在"没有梯度"的前提下制造梯度。如果 `1 − N·V` 本身是常数（平面、退化法线），任何 `P` 都只会改变那个常数的大小。

## 4. 向量归一化的必要性

**它是什么。** `dot`（点积）只有在**两个入参都是单位向量**时才等于夹角余弦。传给它的向量往往不是：顶点属性经插值后长度会缩短，法线贴图解出的法线只在切线空间是单位长度，退化数据还可能产出接近零向量。这属于**顶点/片元数据契约层**的问题：上游没有保证，下游就会算错。

**取值与语义。** 设法线实际长度为 `k`，`V` 是单位向量。点积对第一个参数线性：

```text
(kN̂)·V = k · (N̂·V) = k · cos θ
```

代进 `1 − saturate(dot(N,V))` 得 `fresnel = 1 − k·cos θ`。后果的形状很关键：**不是"整体变亮或变暗"，而是整条等值线被平移**。原本在 `θ₀` 取到的值，现在需要 `cos θ' = cos θ₀ / k` 才能取到：

| 情况 | `k` | 等值线的移动 | 观感 |
|---|---|---|---|
| 向量被插值缩短 | `k < 1` | `θ' < θ₀`，等值线向曲面内侧移动 | 亮圈变宽、整体发灰 |
| 向量被放大 | `k > 1` | `θ' > θ₀` | 亮圈收窄、甚至贴不住轮廓 |
| 退化（长度 → 0） | `k → 0` | 除零 / NaN | 黑块或白块 |

更麻烦的是：**同一个三角形内每个像素的插值长度都不一样**（离顶点越远越短），所以误差是**渐变的**，看起来像"光晕糊了、形状不对"，很难联想到归一化。

**底层机制。**

1. **为什么插值会缩短向量。** 顶点法线在两个顶点之间做的是线性插值，而**单位向量线性插值的模长必然 ≤ 1**（等号仅在两向量相同时成立）。所以插值寄存器里的法线天生不是单位向量。
2. **为什么要做两次归一化。** 顶点阶段归一化是为了不让插值结果**偏向**分量较大的那一侧（几何方向正确）；逐像素归一化是为了让结果**真的是单位长度**（数值正确）。少任何一次都会出问题。
3. **URP 提供的两个工具**，分别解决"法线"和"视线"：
   - `NormalizeNormalPerPixel`（`ShaderLibrary/ShaderVariablesFunctions.hlsl:293-302`）：逐像素 `normalize`；在 `UNITY_NO_DXT5nm && _NORMALMAP` 时改用 `SafeNormalize`，专门防 XYZ 编码法线长度接近 0 时产出 Inf/NaN。
   - `GetWorldSpaceNormalizeViewDir`（同文件 `:125-137`）：透视下返回 `normalize(相机位置 − 片段位置)`；**正交投影下直接返回 `-GetViewForwardDir()`** —— 正交没有"从片段指向相机"的方向可言，这是唯一正确的替代。
4. **顺序约束**：有法线贴图时，法线是"切线空间法线经 TBN 变换到世界空间"得到的。只有切线空间那一份是单位向量，变换后长度受矩阵精度影响，所以归一化必须发生在**变换之后**，不能提前。
5. **`saturate` 兜的是另一类问题**：它把 `pow` 的底数锁在 `[0,1]`。按严重程度排，它挡三件事：
   - **背面**：`Cull Off`（双面）时背面法线朝离开相机的方向，`dot < 0`，`fresnel = 1 − (−0.8) = 1.8`，`pow(1.8, 3)` 会远超 1；钳到 0 后 `fresnel = 1`，背面**整面最亮**。
   - **NaN 传染**：`pow` 对负底数未定义，NaN 一旦进入颜色累加会污染整个像素。
   - **精度越界**：`half` 在移动端/统一精度模型下是 `min16float`（Core 的 `ShaderLibrary/Common.hlsl:132-136`），`dot` 可能落到 `1.0002`，`1 − 1.0002` 得到微负值 —— 对非整数指数就是 NaN。桌面端 `half` 就是 `float`，所以这是**只在移动端暴露**的静默失败点。

**可观察现象与边界。**

- 症状是"边缘光的位置不对、范围偏大、面上有渐变状的不均匀"，而不是明显的破图 —— 属于最难排查的一类 bug。
- `Cull Off` 下背面整面最亮既是兜底也是坑：做能量护盾一类的双面发光时它是特性，普通物体上它会毁掉整个背面。
- **正交相机**：`V` 变成全局常量，只有 `N` 在变，效果仍成立，但**不再随相机位置变化、只随相机朝向变化** —— 这是正交与透视在观感上的一个具体差别。
- **退化数据**：法线贴图被压平、顶点法线为零向量时，`normalize` 可能产出 Inf/NaN；`SafeNormalize` 是 URP 对这个问题的官方兜底。
- 硬边处法线不连续导致的"边缘光断一下"，不属于归一化问题，任何归一化都修不了。

## 5. 颜色属性的 alpha 语义

**它是什么。** 在 ShaderLab 里 `Color` / `Vector` 属性都是**裸 `float4`**：四个通道怎么用、alpha 代表什么，完全由使用者（shader 作者、绑定函数、GUI）决定，引擎不做约定。它属于**属性与数据语义层**，是最容易在"名字像"的两个属性之间踩坑的地方。

**取值与语义。** 同一个工程、甚至同一个引擎里，alpha 可以表示完全不同的东西：

| 约定 | alpha 的含义 | 典型例子 | 行为 |
|---|---|---|---|
| 不透明度 | 表面有多不透明 | 基础色 `_BaseColor.a` | 参与 `clip`、Alpha 混合、预乘 |
| **标量倍率** | 把整个效果乘一遍（0 = 关掉） | 某些效果把发光色写成 `rgb * a` | `a = 0` ⇒ 该项归零，哪怕 `rgb` 是 (10,10,10) |
| **被忽略** | 什么都不表示 | URP 的自发光色 | `SampleEmission(uv, _EmissionColor.rgb, ...)` 传进去的就是 `float3`，alpha 在调用点被丢弃 |
| 遮罩 / 打包 | 由 shader 自定义 | 各种 `float4` 打包属性 | 需要看代码，不能靠名字猜 |

把 `Color` 当"色相 + 标量倍率"是一种**自洽的工程约定**：`rgb` 管色相与相对亮度（`[HDR]` 时允许 > 1，交给 Bloom），`a` 管整体倍率。好处是"关掉某个发光"只需把 alpha 归零，比清空 rgb 更不容易破坏已调好的颜色。

**底层机制。**

- 属性是**数据**，不是类型：`float4` 的 alpha 通道不会因为名字里带 "Color" 就被赋予任何语义。语义来自**它在哪被读**：被 `Alpha()` 读就是透明度，被当作乘数就是倍率，被 `float3` 形参接走就被丢弃。
- 丢弃发生在**函数签名**上：形参类型是 `float3`，调用点的 `.rgb` 就已经把 alpha 丢掉了。这是编译期行为，没有警告。
- `[HDR]` 只影响 Inspector 的取色器与取值范围（允许分量 > 1），既不改变通道数，也不做钳制；真正的钳制发生在颜色缓冲格式上。
- 脚本侧的默认值也参与这张表：`new Color(r, g, b)` 的 alpha **默认是 0**，不是 1。

**可观察现象与边界。**

- ⚠️ 最常见的一类静默失败：脚本里写 `new Color(0f, 1f, 1f)`（想给青色），结果 alpha 为 0 —— 如果该属性按"倍率"约定使用，整个效果**完全消失且不报错**。正确写法是显式给 alpha：`new Color(0f, 1f, 1f, 1f)` 或 `Color.cyan`。
- ⚠️ 反向的坑：把一个按"倍率"使用的颜色属性设成 0.5，会得到一半亮度；而把一个按"不透明度"使用的属性设成 0.5，会得到半透明。两者都在调"alpha"，效果完全不同。
- 当 alpha 同时被用于透明度**和**倍率时，两者会耦合：半透明的表面会一起变暗。要么拆成两个属性，要么在注释里写死约定。
- 边界：逐实例覆盖（§8）会把整个 `float4` 写进去，alpha 也一起覆盖 —— 组件里漏填 alpha 等于把倍率设成 0，这类问题在批量化场景里排查成本很高。

## 6. 发射项在光照方程中的位置

**它是什么。** 发射项（emission）是表面数据里一个额外的颜色（`half3`），语义是"这个表面自己发出的光"。在 URP 的光照方程里它是一个**加法项**，而且位置非常特殊：它在所有光照项**乘过 albedo 之后**才被加上。这一节可以脱离任何具体 shader 独立成立，只看 URP 源码。

**取值与语义。** URP 的 `UniversalFragmentPBR` 先把 `surfaceData.emission` 收进 `lightingData.emissionColor`（`ShaderLibrary/Lighting.hlsl:217-222`），然后交给 `CalculateLightingColor`（`:152-189`，省略 `IsLightingFeatureEnabled` 的分支包裹）：

```hlsl
half3 CalculateLightingColor(LightingData lightingData, half3 albedo)
{
    half3 lightingColor = 0;
    lightingColor += lightingData.giColor;                  // :163  间接光（GI / 光照贴图 / SH）
    lightingColor += lightingData.mainLightColor;           // :168  主光
    lightingColor += lightingData.additionalLightsColor;    // :173  附加光
    lightingColor += lightingData.vertexLightingColor;      //       逐顶点光
    lightingColor *= albedo;                                // :181  ← 所有光照结果乘 albedo
    lightingColor += lightingData.emissionColor;            // :185  ← 发射项在这里进来
    return lightingColor;
}
```

**底层机制（三条推论，全部由这一个位置关系推出）。**

**① 不乘 albedo ⇒ 黑体也能发光。** 加法在乘法之后。如果发射项被写进 `giColor` 或 `mainLightColor`（即 `*= albedo` 之前），那么 albedo = 0 的物体会把发射项乘成 0 —— 从"发光"变成"反射"。而发射项的语义恰恰是"自发光的光不该被自己的反照率过滤"：黑体不反射，但可以发光。这是加法项定义位置的直接后果，不是实现细节。

**② 不吃阴影、不吃 AO。** 阴影与 AO 都是**乘在光源色与 GI 上**的：阴影折进 `lightAttenuation`（`Lighting.hlsl:46` 用它算 radiance，`:77` 把 `distanceAttenuation * shadowAttenuation` 一起传进去）；AO 分两路 —— 直接光照 `light.color *= aoFactor.directAmbientOcclusion`（`ShaderLibrary/RealtimeLights.hlsl:145`），间接光照经 `GlobalIllumination(..., aoFactor.indirectAmbientOcclusion, ...)`（`Lighting.hlsl:290-292`）。它们都在 `CreateLightingData` 之前就折进了 `mainLightColor` / `giColor`，而 `emissionColor` 是从 `surfaceData.emission` 直接搬过来的（`:222`）—— **中间没有任何 AO 或阴影因子碰过它**。所以站在暗处、或被 SSAO 压暗的角落，发射项依然完整。

**③ 它与光照项是"相加"关系，不是"参与光照"。** 由此派生三条常被误解的结论：

- **不产生投影、不影响阴影贴图**：写阴影的 pass 通常 `ColorMask 0`（丢弃颜色写入），也不会去算发射项 —— 发射项是纯颜色，不改变任何几何可见性。
- **不进实时光照传输**：实时管线里 emission 不照亮别人、不进 GI；只有烘焙时它才会被烘进光照贴图 / light probe。
- **不满足能量守恒**：它不是 BRDF 的一部分，不乘 `N·L`、不归一化，可以任意大（HDR），所以它也不会"因为光太强而饱和"。

**⚠️ 关于 `IsLightingFeatureEnabled(EMISSION)`：它不是运行时开关。** 第 185 行的 `if` 所包的函数定义在 `ShaderLibrary/Debug/DebuggingCommon.hlsl:146-153`：

```hlsl
bool IsLightingFeatureEnabled(uint bitMask)
{
#if defined(DEBUG_DISPLAY)
    return (_DebugLightingFeatureFlags == 0) || ((_DebugLightingFeatureFlags & bitMask) != 0);
#else
    return true;      // ← 没有 DEBUG_DISPLAY 时恒真
#endif
}
```

`DEBUG_DISPLAY` 来自 `#pragma multi_compile_fragment _ DEBUG_DISPLAY`，产生两个变体：**正常渲染的那个变体里函数体就是 `return true`，整个 `if` 在编译期被折叠，运行时不存在这个判断。** 它属于渲染调试器的脚手架 —— Rendering Debugger → Lighting 视图可以关掉 Emission 特征单独看 GI 或主光，那是**按设计工作的调试行为**，不是游戏里的开关。要真正关闭发射项，靠的是关键字（§8）或把颜色/贴图置零。

**可观察现象与边界。**

- 发射项**会被后续步骤改写**：URP 在 `UniversalFragmentPBR` 之后还会执行雾混合（`CalculateFinalColor(..., fogCoord)`，`Lighting.hlsl:346`）与可选的颜色预乘（`_ALPHAPREMULTIPLY_ON` 时 `color.rgb *= color.a`）。因此远处物体会被雾色衰减、半透明表面上的发射项会被 alpha 预乘 —— 这些都是"进对位置"顺带拿到的正确行为。
- 想自己 `color.rgb += glow` 也能看到类似亮度，但会漏掉上面两条，并且渲染调试器的 Emission 视图与实际画面不一致。
- 边界：发射项不参与光照，因此它**不会因为场景变暗而变暗**；反过来，它也不会被任何"光照越强越亮"的机制增强。想让它响应光照，那本来就是另一种效果（反射，或用光照去调制自发光）。
- 边界：由于加法发生在 `*= albedo` 之后，**albedo 为纯黑的表面仍然通体发光**。若想让自发光"只出现在贴图指定的区域"，那要靠自发光贴图本身去做遮罩，而不是靠 albedo。

## 7. 加性通道：多个发光来源写进同一个变量

**它是什么。** 着色器里的 `emission` 只是表面数据里的**一个 `half3` 字段**。所有发光来源最终都往同一个字段里 `+=`，这就是"通道"。理解它是加性通道、而不是若干"互相覆盖的层"，是控制发光预算的前提。它属于**光照方程的加法结构**这一层。

**取值与语义。** 典型的三个来源与它们的贡献形式：

| 来源 | 触发方式 | 贡献 | 何时非零 |
|---|---|---|---|
| 自发光贴图 | 关键字（如 `_EMISSION`） | `EmissionMap.rgb * _EmissionColor.rgb`（只取 rgb） | 开关打开且贴图/颜色非黑 |
| 阈值效果的边缘发光 | 关键字（裁切 / 溶解类开关） | 边缘色 `rgb * a * (1 − 边缘因子)` | 只在阈值边界那条带上 |
| 边缘光 | 关键字（如 `_RIM`） | `_RimColor.rgb * _RimColor.a * pow(fresnel, P) * _RimIntensity` | 只在轮廓内侧环带上 |

它们都是 `+=`，所以**最终值就是它们的和**。举例：一个像素同时落在裁切边缘带和轮廓带上，边缘光 `(0.5, 0.7, 1.0) × 1` 撞上默认边缘色 `(2, 0.5, 0.1) × 1`，结果是 `(2.5, 1.2, 1.1)` —— 两个颜色都被冲淡成"发白的边"，若再进 Bloom 就是过曝。

**底层机制。**

- 加法是**可交换**的（顺序不影响结果），但**不可遮盖**：`A + B` 不会因为 A 很亮就让 B 消失。只有不透明物体的颜色写入（后写覆盖前写）才有"遮挡"，而**同一个变量内部的求和不存在先后覆盖关系**。
- 相加之后才发生**量化与钳制**：写进颜色缓冲时受格式限制（HDR 通常是 16 位浮点或 11-11-10 之类），超出范围的部分会被截断或损失精度。Bloom 的亮度阈值与强度决定了这份"超出 1 的能量"最后看起来像光晕还是像白斑。
- 由于 §6 的结论，这几笔光**都不进光照传输**：它们只影响这个表面自己的像素，不会照亮邻物，也不会被阴影衰减。

**可观察现象与边界。**

- ⚠️ 两个来源同时开到高 HDR 亮度 ⇒ 边缘发白、颜色信息丢失（每个通道都被推到 1 以上），加 Bloom 后成为一片光斑。这不是"更好的发光"，而是**动态范围被两笔加法瓜分**。
- 预算做法：**同时最多让一个来源使用 > 1 的 HDR 亮度**，其余留在 `[0,1]`；需要更强时优先调整单个来源的倍率，而不是叠加来源。
- 每个来源都要能被**单独归零**（独立的倍率属性或关键字），否则调参会互相牵制。
- 边界：把发光写进同一个通道，意味着它们共享雾、预乘、调试视图与 HDR/Bloom 的全部下游行为 —— 这既是它的价值（行为一致），也是它的限制（无法单独给某一个来源换路径）。
- 顺带澄清一个常见误解：**"加进 emission 通道" ≠ "把物体变成自发光"**。贴图型自发光通常整面均匀，边缘光只亮在轮廓上；两者机制相同（同一通道），观感完全可以相反。

## 8. 着色器关键字与逐实例数据的分工

**它是什么。** 一个效果参数可以放在三层不同的地方，它们的"可变性"完全不同：**编译期变体**（关键字）、**材质级常量**（CBUFFER 属性）、**逐实例数据**（instancing / BRG）。搞混层次，就会出现"改了没反应""编辑器正常真机丢失""一半实例不发光"这类问题。它属于**关键字与变体编译 + 常量缓冲与批处理**这两层。

**取值与语义。**

| 层 | 谁在改 | 何时生效 | 能表达什么 | 不能表达什么 |
|---|---|---|---|---|
| **关键字** | 材质 / 变体集合 | **编译期**：变体在构建时展开成独立程序 | 开 / 关、多选一模式 | 数值；**不能逐实例** |
| **材质属性**（`UnityPerMaterial` CBUFFER） | 材质球 / 脚本 `SetFloat` | 运行期，但**每材质**一份 | 颜色、强度、阈值等数值 | 同一材质内不同实例取不同值 |
| **逐实例数据** | GPU instancing 的 buffer / BRG 的逐实体属性 | 运行期，**每实例**一份 | 颜色、强度等数值 | **不能替代关键字**（它只是数据） |

```shaderlab
Properties
{
    [Toggle(_RIM)] _RimOn("Rim Glow", Float) = 0
    [HDR] _RimColor("Rim Color", Color) = (0.5, 0.7, 1.0, 1.0)
    _RimPower("Rim Power", Range(0.25, 8)) = 3.0
    _RimIntensity("Rim Intensity", Range(0, 16)) = 1.0
}

HLSLPROGRAM
#pragma shader_feature_local_fragment _RIM     // 只在片元阶段生成这两个变体
ENDHLSL
```

**底层机制。**

1. **关键字是编译期展开，运行时没有"开关"可读。** `#pragma shader_feature_local_fragment _RIM` 会生成两个程序：定义了 `_RIM` 的和没定义的。`#if defined(_RIM)` 在编译期就被折叠掉，运行时不存在分支判断。因此"开关"只能通过**切换变体**实现，而变体是材质级的 —— 无法逐实例切换。
2. **`shader_feature` vs `multi_compile`。** `shader_feature` 的变体集合由**实际使用它的材质**决定，打包时会剥离没被任何材质启用的组合；`multi_compile` 则总是全部保留，供运行时按需切换（管线关键字几乎都是它）。这解释了一个经典现象：只在运行时 `EnableKeyword` 而没有任何材质真正开过该关键字 ⇒ **编辑器里正常、打包后变体不存在**。
3. **`_fragment` 等阶段后缀**限制变体生成在哪个阶段。若把用到该宏的代码挪到别的阶段，那里根本看不到这个宏 —— 编译能过，结果却不是你想的。
4. **逐实例数据的取样方式决定了"缺省"语义。** GPU instancing 走 instancing buffer，缺失时通常回落到材质常量；而 **BRG（BatchRendererGroup）/ Entities Graphics 这类批量路径会在地址 0 保留一块全零区域**，没挂对应组件的实体从那里读到 **0**，而不是材质球的值。所以"默认值"必须设计成"关闭态"（例如颜色全零），否则漏数据的实体会呈现出意料之外的外观。
5. **成本在变体数量上。** 关键字相乘会膨胀变体集合（编译时间、包体、运行时切换的 PSO 创建开销）。这也是 `shader_feature`（按需保留）存在的理由。

**可观察现象与边界。**

- ⚠️ **编辑器与真机不一致**：运行时开关键字、打包后失效 —— 见第 2 点。上线用的效果至少要有一个材质在构建里真正开过该关键字。
- ⚠️ **"一批实例里只有一部分要发光"做不到**（关键字是材质级的）：正确做法是把不发光那些实例的**数值**（强度或颜色倍率）设为 0，用"亮度归零"模拟"关闭"。
- ⚠️ **漏组件的实体读到 0**：颜色类属性全零恰好等于关闭，通常安全；但如果某个属性的 0 是"全黑 / 全透明 / 阈值为 0"这类异常值，就会出现"加了组件却不生效"或"整片变黑"。请在批量路径里显式给初值。
- **脚本改数值不会切变体**：`SetFloat` 只写常量，不改关键字。`[Toggle]` 属性抽屉会在 Inspector 绘制时同步关键字，但纯脚本路径需要自己调 `EnableKeyword` / `DisableKeyword`。
- 边界：逐实例数据只覆盖**数值**；凡是需要改代码路径（是否调用某个函数、是否 `clip`、是否多采样一张贴图）的效果，都必须是关键字，也就天然是材质级的。

## 9. 小结

| 知识点 | 一句话结论 | 主要边界 |
|---|---|---|
| 菲涅尔与 Schlick | 取 `F0 = 0` 后是纯形状函数，用来做轮廓蒙版，不是 BRDF | 不守恒、不响应光源 |
| `N·V` | 视线与法线夹角余弦，度量轮廓可见性 | 平面无梯度、硬边不连续 |
| `pow` 整形 | 在角度轴上平移等值线，`θ = acos(1 − 0.5^(1/P))` | 上界 90°、`P = 0` 使变量消失 |
| 归一化 | `(kN)·V = k(N·V)`：长度误差使边缘位置整体偏移 | 正交相机、退化法线、移动端 half |
| alpha 语义 | `float4` 是裸数据，语义由读取点决定 | 倍率与透明度会互相耦合 |
| 发射项位置 | `*= albedo` 之后的加法尾巴：不乘 albedo、不吃阴影 / AO | 不投影、不进 GI、被雾与预乘改写 |
| 加性通道 | 多笔发光相加，不能互相遮盖 | HDR 预算被瓜分、过曝 |
| 关键字与逐实例数据 | 关键字是编译期、材质级；逐实例只能改数值 | 打包剥离、缺组件读 0 |
